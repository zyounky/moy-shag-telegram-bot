# Отдельная служба на Debian с systemd

Служба не открывает входящие порты: Telegram используется через long polling.
Нужны Python 3.11+, venv и исходящий HTTPS к Telegram и выбранному API модели.
Процесс работает от отдельного системного пользователя `moy-shag-bot` без входа в shell.
Docker и изменение соседних служб не нужны.

Размещение:

- `/opt/moy-shag-bot/releases/<commit>/` — код конкретной версии, только чтение;
- `/opt/moy-shag-bot/current` — ссылка на выбранную версию;
- `/opt/moy-shag-bot/venv/` — отдельное окружение с requirements.txt;
- `/opt/moy-shag-bot/data/catalog.jsonl` — только подготовленный открытый каталог;
- `/etc/moy-shag-bot.env` — конфигурация, root:root, права 0600;
- `/var/lib/moy-shag-bot/state.db` — состояние, каталог создаёт systemd;
- `/opt/moy-shag-bot/backups/` — резервные копии перед изменениями, права 0700.

Исходный дамп, таблицы пользователей, локальный SSH-ключ и GitHub-учётные данные
на сервер не копируются. Перед изменением существующих файлов сохраняйте копии
конфигурации, unit-файла, текущей версии и согласованную SQLite-копию состояния
через `sqlite3.Connection.backup`, а не копированием открытой базы.
Перед созданием системного пользователя сохраните закрытые копии файлов учётных
записей `/etc/passwd`, `/etc/group`, `/etc/shadow`, `/etc/gshadow` в каталоге backup
с правами 0700; не выгружайте и не выводите их содержимое.

Подготовьте venv и установите закреплённые зависимости. Проверьте каталог командой
`venv/bin/python -m assistant_bot --check` с путями к каталогу и временной SQLite.
Проверьте unit через `systemd-analyze verify`. Не выводите `.env`, `systemctl show`
с окружением или параметры запросов с ключами в отчёт.

Для переноса состояния остановите единственный локальный polling-процесс, сделайте
SQLite backup и загрузите его на сервер. На этапе подготовки серверный бот не
должен обращаться к `getUpdates`: два процесса с одним токеном конфликтуют.
Передайте каталог состояния и SQLite пользователю `moy-shag-bot`, права 0700/0600.
Запустите только новую `moy-shag-bot.service` после
проверок. Не перезапускайте соседние службы.

Ограничения `LLM_TEST_CHAT_IDS`, `LLM_TEST_EXPIRES_AT`, `LLM_MAX_REQUESTS` сохраняются
при переносе. Хостинг не продлевает разрешение отправки материалов внешней модели.
Для дальнейших тестов нужен согласованный срок. `LLM_BUDGET_PATH` в unit-файле
сохраняет число API-попыток в отдельной SQLite, включая неудачные запросы.
Перезапуск не обнуляет бюджет в пределах того же провайдера, списка тестеров и
срока. Новый согласованный срок создаёт отдельный бюджет. Не изменяйте срок или
список тестеров для обхода ограничения. Кешированные ответы API-попытку не тратят.

Проверка после запуска: статус только новой службы, её короткий журнал без ключей,
один polling-процесс и отсутствие Telegram 409. Журнал старта подтверждает запуск,
но не заменяет пользовательский тест ответа в Telegram.

При проблеме остановите новую службу и верните сохранённую версию и состояние.
Остановка/перезапуск существующей серверной службы согласуется с владельцем.
